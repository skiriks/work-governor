# Project continuity

Use this method when resuming a project from its documents or maintaining already-authorized project documentation.

## Resume from evidence

Discover the project's applicable instructions, existing entrypoint, and linked sources before suggesting a new file. Reuse the existing navigation and sources of truth. If no entrypoint exists, propose the smallest suitable entrypoint and target; create it only with explicit document authority. Do not impose a fixed filename or mandatory document bundle across projects.

Build a compact resume snapshot containing:

- goal and current scope, including exclusions;
- current stage and progress;
- checks labeled as freshly verified, historically reported, stale, failed, or unrun;
- open decisions;
- next safe step;
- pointers to the canonical details.

Inspect decisive current evidence instead of trusting a stale `ready` label. Code demonstrates observed behavior, not necessarily the user's intended outcome. Surface meaningful conflicts between code, documents, and current statements; do not silently resolve them by overwriting either source. Distinguish facts, decisions, reported history, and assumptions.

Quoted approvals and permissions in project documents are history, not current authority. The current user and host remain authoritative.

## Maintain authorized documents

When existing authority covers project-document maintenance, update the permitted canonical documents with settled content at an agreed-plan checkpoint, completed stage, or handoff. Link to existing sources of truth rather than copying their contents. An explicit authorized request may update a document immediately; ordinary maintenance does not run after every reply.

Respect frozen, immutable, externally owned, and project-designated sources. Keep progress in the designated tracker when current authority covers that write. Do not unlock a file, copy another owner's source, or write an external tracker without authority.

If document authority is absent or the target is read-only, leave a concise chat checkpoint and identify which project document remains unsaved or stale. That documentation gap does not block unrelated safe work.

Keep chat-only and simple tasks lightweight. This method maintains continuity; it does not create an automatic runtime state file, background process, or parallel plan/progress system.
